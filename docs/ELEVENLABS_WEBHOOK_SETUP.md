# ElevenLabs Brittany → RestaurantCall AI (Phase 5 preview adapter)

## Status and scope

This is a **preview / staging implementation** on `feat/elevenlabs-brittany-webhooks`. It adds an authenticated tool endpoint and an authenticated session-binding endpoint in the existing Next.js app, reuses the existing Neon `call_sessions`, `draft_carts`, `menu_items`, `restaurants`, `promotions`, and `orders` tables, and deliberately keeps actual order creation **disabled**. No production deployment or webhook registration has been performed.

Why checkout is disabled: Phase 4 uses Telnyx Conversation Relay `tokensPlayed` evidence to prove the entire financial review reached the caller. ElevenLabs ElevenAgents does not automatically supply this equivalent evidence through a generic webhook tool. An LLM-supplied boolean, transcript, or message that says 'I read the order' is **not** proof of playback. Do not loosen checkout safety until a reliable provider-backed playback completion mechanism has been designed, tested and reviewed.

## Install the code

Copy these files into the Phase 4 repository at their same relative paths:

- `frontend/lib/elevenlabs-tools.ts`
- `frontend/app/api/elevenlabs/tools/route.ts`

The adapter has been integrated into the Phase 5 branch, but live ElevenLabs provider acceptance has not been performed. Run `cd frontend && npm ci && npm run typecheck && npm run test:unit && npm run build` and fix any type / integration failures before exposing the endpoint. Confirm migrations 0001–0008 are in place on a **disposable Neon branch**. Never point the preview adapter at production orders without explicit approval.

Set these environment variables on a Vercel **preview** deployment (not production):

- `DATABASE_URL` — connection string to disposable Neon branch, never reveal or paste into agent prompt.
- `RESTAURANT_ID` — restaurant UUID in that staging database.
- `ELEVENLABS_WEBHOOKS_ENABLED=true` — enables endpoint. Leave false/absent in production.
- `ELEVENLABS_TOOL_API_KEY` — independently generated random secret of 32+ characters; store in Vercel encrypted settings and ElevenLabs Secret header. Never commit it.

Retain the existing API/session, payment and notification environment settings. Do not change the working Telnyx → ElevenLabs SIP connection or G711U codec.

## Tool endpoint

`POST https://<verified-preview-domain>/api/elevenlabs/tools`

Headers:

- `Content-Type: application/json`
- `Authorization: Bearer <ELEVENLABS_TOOL_API_KEY>` stored as a secret header in ElevenLabs.

Each tool supplies `tool` (fixed string) and `conversation_id` mapped from `{{system__conversation_id}}` (not generated by the LLM). The conversation must already be bound to an active `call_sessions` row through `POST /api/elevenlabs/session`, or the request is rejected. The tool endpoint does not create sessions from model input. Binding requires a trusted server-side caller that supplies the verified Telnyx/SIP `provider_call_id`; it is disabled by default.

### Tool definitions to enter under ElevenLabs Agent → Tools → Add Tool → Webhook

Use method `POST`, the endpoint above, the secret Authorization header, JSON body type, and the corresponding `name`, `description`, fixed `tool` field, and LLM-supplied parameters from `config/elevenlabs-webhook-tool-blueprints.json`. These JSON entries are a **manual configuration blueprint**, not a claim that ElevenLabs accepts this file as a direct import artifact. In the ElevenLabs UI, assign the `conversation_id` parameter as a dynamic variable, not an editable model value. Use `{{system__conversation_id}}`; check rendered request samples in a test conversation.

1. `search_menu`: send `query` (optional, search text). Returns up to 20 matches with actual IDs and prices.
2. `update_cart`: send `item_id` (a returned UUID), `operation` (`add`, `set`, `remove`), `quantity` (integer 1–20 for add/set).
3. `get_cart`: no extra values.
4. `set_customer_details`: `customer_name`, optional `customer_phone` E.164, optional `name_confirmed`.
5. `set_notification_preference`: `channel` (`none`, `sms`, `call`), `consent` boolean. Non-none requires a previously confirmed callback phone number. Consent is provisional and doesn't dispatch notifications.
6. `review_order`: returns a *preview* itemization including promotion and tax totals from the existing quote engine. It does not place an order.
7. `confirm_order`: always returns `CHECKOUT_DISABLED`. **Do not add this tool to Brittany's live production agent.** Include only in preview testing and instruct Brittany never to claim success.
8. `get_order_status`: reads an order only if actually associated with that conversation's database session. Preview sessions normally return `NO_PLACED_ORDER`.

### Example preview calls

```bash
curl -sS -X POST 'https://<verified-preview-domain>/api/elevenlabs/tools' \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $ELEVENLABS_TOOL_API_KEY" \
  --data '{"tool":"search_menu","conversation_id":"conv_test_12345678","query":"shawarma"}'
```

```bash
curl -sS -X POST 'https://<verified-preview-domain>/api/elevenlabs/tools' \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $ELEVENLABS_TOOL_API_KEY" \
  --data '{"tool":"confirm_order","conversation_id":"conv_test_12345678"}'
```

Expected `confirm_order`: HTTP 409 with `code: CHECKOUT_DISABLED`, no database order created.

## Existing notification system

The Phase 4 source already has `frontend/app/api/telnyx/messaging/route.ts`, signed Telnyx event processing in `frontend/lib/provider-events.ts`, notification jobs in `frontend/lib/operations.ts`, status changes in `frontend/lib/repository.ts`, and an existing *Telnyx TeXML* ready-call path. Do **not** create duplicate messaging webhooks or SMS queues. The current ready-call implementation uses Telnyx TeXML, **not** ElevenLabs SIP outbound. Switching outbound delivery to Brittany requires a separately reviewed provider adapter, associated consent, verified outbound routing and a controlled test.

Before enabling actual texts: confirm phone number messaging capability, assigned Telnyx Messaging Profile, relevant US A2P registration, callback signatures, STOP handling, sender identity, and queue processing frequency. The existing worker gates delivery via `SMS_DELIVERY_ENABLED` and `OUTBOUND_UPDATES_ENABLED`; keep disabled until ready. Existing `frontend/app/api/telnyx/messaging/route.ts` is the callback URL to register after verifying the deployment's domain.

## Session binding

Before a tool call, a trusted telephony or session-initiation service must call `POST /api/elevenlabs/session` with `Authorization: Bearer $ELEVENLABS_SESSION_BINDING_KEY` and `{ "conversation_id": "{{system__conversation_id}}", "provider_call_id": "<verified Telnyx call id>" }`. Set `ELEVENLABS_SESSION_BINDING_ENABLED=true` only in an isolated environment. The route validates the active tenant call session, expiry and uniqueness before recording the ElevenLabs conversation ID. It never trusts a caller-provided restaurant ID or phone number.

The tool endpoint remains disabled until `ELEVENLABS_WEBHOOKS_ENABLED=true` and a random `ELEVENLABS_TOOL_API_KEY` of at least 32 characters is configured. The exact public URL is intentionally omitted until a verified preview deployment exists.
